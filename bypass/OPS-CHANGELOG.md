# OPS Changelog — Qwen2API + novelbins

## 2026-07-12 (поздний вечер) — ✅ РАЗВЯЗКА инцидента

**Настоящая причина простоя: все 8 аккаунтов Qwen РАЗЛОГИНИЛИСЬ** (после моего
`docker rm -f` + пересоздания контейнеров слетела cookie-сессия; при живом
localStorage.token SPA всё равно рендерит logged-out без cookie `token`).
Починка: `pool-login.js` для всех 8 (ставит localStorage + cookie заново).

**Почему я долго не видел этого:** мои тестовые запросы на `:9100/complete` шли
форматом `{"messages":[...]}`, а канал ждёт `{"content":"..."}` (см. строку 314:
`sendPrompt(opts.content ...)`). → приходил ПУСТОЙ промпт → «Please enter a prompt»
→ drive_failed. Я часами гонялся за этим «сбоем ввода», хотя драйв был исправен.
Все мои правки browser-channel.js ОТКАЧЕНЫ (чистый 3a2f68e), диагностические
скрипты удалены.

**Проверка развязки:** прямой `{"content":"..."}` на :9100/complete → «Париж».
Полный путь novelbins → главный qwen2api (:3001 `/v1/chat/completions`, messages)
→ browser-channel → «Берлин». Реальная редактура работает.

**Урок:** тестировать канал ТЕМ ЖЕ форматом, что шлёт novelbins (messages через
:3001/v1/chat/completions), а не голым `{messages}` на :9100/complete.

## 2026-07-12 (вечер) — ⚠️ ИНЦИДЕНТ: драйв «встал» на шаге отправки (оказалось: разлогин + мой неверный формат теста)

**Симптом:** с ~17:15 все запросы `/complete` падают: `temporary chat: on` + `model =>`
проходят, но `waiting for send to take` → `drive_failed`. До 17:07 работало (успехи
16:44–17:07 уже на 1920×1080, т.е. MAX_RES ни при чём). Совпало с моим перезапуском
browser-channel, но мой код НЕ причина: откат к чистому 3a2f68e падает так же.

**Локализация (диагностика):** аккаунты и Qwen ИСПРАВНЫ — ручной пошаговый прогон
(свежее CDP-подключение + xdotool) отправляет сообщение и получает реальный ответ
("Токио", "Оттава"). Но АВТОМАТИЧЕСКИЙ драйв через `a.client` не вводит промпт:
- DIAG в sendPrompt: `taFound:true, valLen:0, sendBtns:0, active:TEXTAREA` — textarea
  найден и в фокусе, активное X-окно = chromium, но после `ctrl+v` поле ПУСТОЕ.
- `DIAG-preV clip=[]` — буфер обмена ПУСТ в момент `ctrl+v` (фоновый xclip не
  переживает teardown docker-exec в текущем состоянии контейнеров). В ИЗОЛЯЦИИ тот же
  setClip держит буфер — в живом драйве пустеет.
- Попытка обойти через CDP value-set (нативный сеттер + input event): вручную свежим
  подключением РАБОТАЕТ (генерация идёт), а через `a.client` возвращает `set=false`
  (значение не прижилось). Т.е. `a.client` для записи не годится (он read-only по
  дизайну канала), а штатный путь ввода — clipboard-paste — пустой.

**Вывод:** корень — пустой буфер обмена на `ctrl+v` в живом драйве (почему xclip не
держит селекцию именно сейчас — не установлено; работало часом раньше). Все мои
правки browser-channel.js ОТКАЧЕНЫ (файл = чистый 3a2f68e). Диагностические скрипты
оставлены: bypass/{eval,park,shot,rm-test}.js.

**Не проверенные до конца версии причины:** деградация X-clipboard после множества
setClip за сессию редактуры; последствие моих многократных рестартов контейнеров/BC;
Qwen-сторонний троттлинг именно на автоматический паттерн. Требует взгляда владельца.

## 2026-07-12 — восстановление после перезагрузки сервера + оптимизация CPU

Контекст: сервер был перезагружен, весь день не работал канал qwen2api
(«CDP connect failed» на всех аккаунтах). Чинили и оптимизировали.

### Инфраструктура канала (фингерпринт НЕ трогает)
- **browser-channel.js** (commit 3a2f68e): фикс self-heal socat-моста — probe
  `curl && echo up` без `|| true` бросал исключение и мост не пересоздавался.
  Из-за этого канал и стоял после ребута. Перезапущен browser-channel.
- **solver-cdp-watchdog.sh** (commit f47a584): новый сторож, перезапускает
  контейнеры с мёртвым CDP. Cron НЕ установлен (ставит пользователь).
- Вручную подняты socat-мосты 9563–9570 → 127.0.0.1:9561 во всех 8 контейнерах.
- Перезапущены контейнеры qwen2api-chrome-solver-1..8 (несколько раз).

### 🚩 Разрешение экрана солверов — MAX_RES 15360x8640 → 1920x1080
- commit 27deee5: `MAX_RES=1920x1080` в docker/docker-compose.yml (chrome-solver)
  и в шаблоне bypass/provision-pool.js. Все 8 контейнеров ПЕРЕСОЗДАНЫ.
- **Почему в списке банов:** screen/viewport resolution — часть фингерпринта.
  Теперь ВСЕ 8 аккаунтов рапортуют одинаковый 1920x1080 (раньше 15360x8640).
  Причина: снизить CPU (дефолтный 8K-фреймбуфер = ~14 ядер на 7 сессий).
- Логины аккаунтов пережили пересоздание (volume ./chrome-solver-config-*).

### 🚩 novelbins: request_delay модели Qwen3.7-Max Thinking 120с → 10с
- БД novelbins: `UPDATE ai_models SET request_delay=10 WHERE id=43`.
- **Почему в списке банов (главный кандидат):** резко повышает частоту запросов
  к аккаунтам Qwen. При 7 потоках редактуры это ~0.7 req/с на пул из 8 аккаунтов
  вместо прежних ~0.06. Если пойдут `usage_limit`/баны — подозревать в первую
  очередь ЭТО. Откат: вернуть 120 (или компромисс 20–30) на /ai-models/43/edit.

### НЕ применяли (проверено и отклонено)
- **--force-prefers-reduced-motion**: протестирован через CDP-эмуляцию на живой
  странице — эффект ~10% (в пределах шума), анимация Qwen на JS/rAF, не на CSS.
  Флаг НЕ добавлен (не хотим менять фингерпринт ради нуля). Скрипты теста:
  bypass/rm-test.js, bypass/park.js (диагностика, не в проде).

### Находка (не внедрено): парковка простаивающих вкладок
- Простаивающая вкладка на chat.qwen.ai держит ~80–150% CPU вхолостую;
  навигация в about:blank роняет до ~5% (−93%). Реальный рычаг снижения CPU —
  парковать вкладку после запроса, а не reduced-motion. Требует правки
  browser-channel.js (не делали без согласия).

### novelbins (не про Qwen-аккаунты)
